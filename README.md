# Сплавы · версия 0.7.0 · этапы 4 и 5

### Лодки, трансфер и работники

В карточке выезда добавлены «Байдарки», «Трансфер» и «Работники». В «Обзоре» видна готовность рассадки, проезда и инструкторов с переходами к нужным действиям. Приложение ведёт один организатор; работникам отдельные аккаунты не создаются.

Первое заполнение: «Байдарки» → «Парк» → «Применить исходные данные». Будут добавлены две большие лодки, наш автобус на 30 мест, второй автобус с выбором 16/17/19/20 мест в рейсе, такси на 4 места, Лиза, Анна Орлова и Варя. Для «Каяк РФ» и «Майгун» нажмите «Добавить несколько лодок» и укажите фактическое количество. Ориентиры 20–25 и больше 20 не превращаются в подтверждённое наличие автоматически. Учётные номера внутренние, их можно изменить.

- Большие лодки поддерживают 3 обычных места либо 4 места, где четвёртое — для ребёнка ростом не выше 130 см. Для этого места заполните рост и возраст участия; в данном этапе ребёнок определяется как возраст меньше 18 лет.
- «Каяк РФ» — 2 места или 2 + 1. Дополнительное место требует заполненных роста не выше 155 см и веса не больше 50 кг; оно доступно и небольшому взрослому.
- «Майгун» — 2 места. Инструкторы входят в экипажи и занимают обычные места.

Бронь задаёт время, подготовку до начала и освобождение после окончания. Сервер проверяет пересечения одного физического ресурса на разных выездах; соседние интервалы полуоткрытые. Каждое назначение места проверяет текущую версию, статус участия и вместимость. Перенос в другую лодку освобождает прежнее плановое место одной командой. При отмене участия или изменении параметров, несовместимых с дополнительным местом, плановая рассадка освобождается. Факты выхода на воду сохраняются.

В «Трансфере» создайте рейсы туда и обратно, укажите точки посадки и при необходимости работника, ответственного за рейс. Поездки независимы: один человек может ехать туда автобусом, обратно самостоятельно. Для участников и работников можно выбрать номер места. Привязка работника к карточке человека предотвращает двойное назначение одного человека как работника и участника. Отметка посадки и выхода на воду — отдельный факт с автором, устройством и временем. Для изменения отметки требуется причина.

Поздняя отмена либо перенос после отметки присутствия создают видимое расхождение. Решение «Факт верен» сохраняет присутствие; «Ошибка отметки» добавляет исправляющий факт, оставляя исходный в истории. Место с отмеченным фактическим присутствием другого человека нельзя незаметно занять новой записью. Разбор выполняет единственный организатор; разбор ожидающих изменений становится доступен после получения подтверждённого состояния.

В «Работниках» ведутся специализации, доступность и интервалы работы. Лиза — склад; Анна Орлова — кухня лагеря; Варя имеет специализации обеих и подмену. Кадровый резерв: водители УАЗа 3–4, повара на выезде 3–4, инструкторы 3–6, работник лагеря / резерв инструктора — 1. Это ориентиры справочника, а не требуемое количество на каждом выезде. При 35 и более подтверждённых клиентах нужны два инструктора на воде; для группы с большим количеством детей включите соответствующий признак. Количественный порог «много детей» не придуман. Работник лагеря в резерве не считается вторым инструктором до включения в состав и экипаж.

Все разделы читают локальную SQLite, сохраняют команды в прежнюю устойчивую очередь и обмениваются автоматически. Подтверждённый план и предварительные изменения различимы. Схема SQLite остаётся v3; новые связанные данные входят в согласованный снимок выезда. PostgreSQL обновляется добавочными миграциями `20261106001200`–`20261106001400`; существующие профили, платежи и очереди не очищаются. Запуск локального сервера и конфигурация окружения описаны ниже.

```powershell
.tools/supabase-cli/node_modules/.bin/supabase.cmd migration up --local
$env:SPLAV_SUPABASE_KEY = (Get-Content -Raw config/workspace-a.local.json | ConvertFrom-Json).SUPABASE_ANON_KEY
python scripts/stage45_acceptance.py
flutter test test/operations_test.dart
flutter test test/operations_live_test.dart
flutter test integration_test/stage45_device_test.dart -d windows --dart-define-from-file=config/workspace-a.local.json
flutter test integration_test/stage45_device_test.dart -d emulator-5554 --dart-define-from-file=config/workspace-b.local.json
```

Серверная проверка создаёт отдельную явно названную тестовую команду `Проверка этапов 4–5 (вымышленные данные)`. Её парк не смешивается с рабочим парком. SQL-сценарий подготавливает эту команду и для последующих клиентских проверок. Платформенные проверки используют отдельные локальные профили. Подробный результат — в `ОТЧЁТ-ЭТАПЫ-4-5.md`.

Сборки: Windows — `build/windows/x64/runner/Release/splav.exe`; Android — `build/app/outputs/flutter-apk/app-release.apk`. Для переноса Windows копируйте весь каталог Release. Профиль workspace-a подключается к локальному серверу 127.0.0.1, workspace-b — к 10.0.2.2 из Android-эмулятора; для физического телефона требуется доступный ему адрес сервера и соответствующая конфигурация сборки.

### Компактный состав и предоплата

Состояние обмена находится под названием страницы в шапке; нажмите на него для подробностей. Обновление остаётся справа сверху, на F5 и свайпом вниз. Синхронизация автоматическая.

На вкладке «Участники» состав сгруппирован по компаниям. Заголовок показывает общую согласованную стоимость, чистую оплату, остаток или переплату и нераспределённые деньги. Поиск и фильтры скрывают строки, но сохраняют полные итоги компании. На широком экране используется компактная таблица; на телефоне — строки с переносом данных и действий. Статусы и оплата сопровождаются цветом и текстом.

Фильтры оплаты: «Нет предоплаты» — платное участие без зачтённых денег; «Есть предоплата» — частичная оплата; «Оплачено полностью» — зачтено не меньше согласованной стоимости. Бесплатное участие помечено отдельно и видно в фильтре «Любая». Возвраты и исправления учитываются в этих же расчётах. Историческая сумма первого взноса отдельно не выделяется: предоплатой считается текущая частичная оплата.

Быстрая предоплата — **500 ₽ на человека**. Для новой компании из трёх платных участников подставляется 1500 ₽ с распределением по 500 ₽. Уже зачтённые суммы вычитаются; для участия дешевле 500 ₽ подставляется его стоимость. Полная оплата подставляет остаток. Перед сохранением можно изменить сумму и распределение. Отменённые участия и лист ожидания не входят в автоматическое предложение; их деньги доступны в разделе «Оплаты». При нераспределённой оплате сначала распределите уже полученные деньги. «Своя сумма» доступна для ручного ввода, включая переплату.

Нажатие быстрой кнопки открывает форму проверки. Сохранение создаёт обычный платёж в прежней устойчивой очереди и отправляет его автоматически. Версия SQLite, формат платежей и серверные миграции не изменены; существующие данные и ожидающие операции используются без переноса. Термин «Компания» заменяет «Заявка» для объединения людей в интерфейсе; сохранённые пользователем имена не переименовываются.

Проверки интерфейса: `flutter test test/finance_ui_test.dart`. Платформенный сценарий этапа 3 дополнен оплатой из нового списка с последующим подтверждением сервера.

### Стоимость и платежи

В карточке сплава откройте «Оплаты» и выберите заявку. Стоимость каждого участия зафиксирована при записи: изменение базовой цены сплава действует на новые записи. Кнопка «Изменить стоимость» задаёт согласованные суммы с причиной, сохраняя историю.

«Получить оплату» фиксирует одно получение денег на заявку. В той же форме распределите сумму между участниками: отдельные зачтённые суммы не прибавляются к поступлениям повторно. Оставшуюся часть можно распределить позже. Частичная оплата показывает остаток, отрицательный остаток — переплату. Расчёт по человеку отличается от расчёта заявки, пока часть денег не распределена.

«Записать возврат» уменьшает чистую оплату. Возвращаемую распределённую сумму снимайте с соответствующих участников. Возврат ограничен ранее полученными деньгами, а зачтённая человеку сумма не может стать отрицательной. Для исправления проведённой записи используйте «Исправить с причиной»: исходный платёж сохранится, появятся сторно и верный вариант либо аннулирование без замены. Это исправление учётной записи; фактический возврат отмечается отдельным действием.

Отмена участия сохраняет согласованную стоимость и оплату. Если стоимость отменённого участия должна стать нулевой, укажите 0 с причиной; возврат денег запишите отдельно. Ожидание и роль инструктора сами по себе проведённые суммы не изменяют.

Все суммы хранятся целыми копейками. Пока очередь не подтверждена, экран помечает расчёт как предварительный и показывает подтверждённую сервером чистую оплату. При конфликте сравните предложенную стоимость с серверной, затем повторите или отмените локальное действие. Зависимые локальные действия при разборе отменяются с пояснением.

Миграции `20261106000900`–`20261106001100` добавляют неизменяемый журнал денег, версии распределения и историю стоимости. Они применяются поверх прежних данных. Локальная схема SQLite остаётся v3: платежи, распределения и история сохраняются в согласованном снимке выезда, команды — в прежней транзакционной очереди. Вариант снимка с финансовыми данными помечен отдельно, чтобы отсутствие ещё не загруженной оплаты не отображалось как нулевая оплата.

```powershell
$env:SPLAV_SUPABASE_KEY = '<local publishable or anon key>'
python scripts/stage3_acceptance.py
flutter test --no-pub test/finance_live_test.dart
flutter test integration_test/stage3_device_test.dart -d windows --dart-define-from-file=config/workspace-a.local.json
flutter test integration_test/stage3_device_test.dart -d emulator-5554 --dart-define-from-file=config/workspace-b.local.json
```

Сквозной сценарий создаёт вымышленную семью и проверяет перезапуск с очередью, потерю уже принятого ответа, обрыв между подтверждением и снимком, независимые оплаты двух клиентов, возврат и корректировку. SQL-проверка дополнительно проверяет конкурентное перераспределение и запрет доступа к чужой заявке. Подробный результат — в `ОТЧЁТ-ЭТАП-3.md`.

### Новая Windows-сборка

Готовый вариант с обновлённым интерфейсом: `build/windows/x64/runner/Release/splav.exe`. Для переноса копируйте весь каталог `Release`, включая библиотеки и `data`. Это обычная сборка Release; каталог `Debug` используется платформенными тестами и не является основной ссылкой для запуска.

```powershell
Start-Process build/windows/x64/runner/Release/splav.exe
```

Главная показывает сплавы, пересекающие «вчера — сегодня + 7 дней». «Все сплавы» открывает полный список с поиском, диапазоном дат и состоянием. В календаре доступны месяц с крупными ячейками событий и недельный вид. В таблицах даты содержат дни недели; жёлтый обозначает заполнение от 80%, красный — полный сплав или превышение. Подписи поясняют значение цвета.

Лимит клиентов теперь является ориентиром: добавление, подтверждение и изменение роли сверх лимита разрешены. Предупреждение показывается в карточке и составе. В заполнение входят клиенты со статусами «Заявка» и «Подтверждено»; ожидание и инструкторы учитываются отдельно. Прежние отказы по старому правилу можно повторить отдельным действием — сохранённый результат старого UUID остаётся неизменным.

Обмен автоматический при сохранении, возвращении в приложение и периодически. Потеря связи переводит отображение на локальные данные, а попытки возобновляются автоматически. Переключателя «Без сети» в рабочем интерфейсе нет. Обновление доступно справа в шапке и по F5, на Android — также свайпом вниз. Ближайшие выезды загружаются автоматически, остальные — при открытии. Значок в таблице показывает готовность состава к работе без связи.

```powershell
flutter build windows --no-pub --release --dart-define-from-file=config/workspace-a.local.json
flutter build apk --release --dart-define-from-file=config/workspace-b.local.json
```

Для Release на Android HTTP разрешён только локальным адресам эмулятора и loopback. Рабочий удалённый сервер должен использовать HTTPS. Debug-сборка допускает HTTP для локальной разработки. Миграция `20261106000800_advisory_capacity.sql` меняет правило лимита и добавляет показатели заполнения в каталог без удаления данных.

При переходе между нативными тестами и Android Release не используйте `--no-pub`: зафиксированный Flutter пересоздаёт регистрацию платформенных плагинов на этом шаге. Иначе после теста в обычной сборке может остаться ссылка на исключённый тестовый плагин. На локальных проверках без смены режима допустим `--no-pub`.

Описание этапа 2 ниже сохраняет контекст исходной реализации; перечисленные выше уточнения заменяют прежний отказ при превышении лимита и ручное переключение режима сети.

Рабочий режим содержит вход организатора, список и календарь выездов, справочник людей, совместные заявки, параметры участия и лист ожидания. Семья создаётся одной заявкой с отдельным участием каждого человека. Контакт может не участвовать в сплаве. Подтверждение выбранных участников выполняется целиком с проверкой лимита на сервере. Локальные изменения и конфликты видны отдельно от подтверждённого состава.

Команды выполняются в PowerShell из корня проекта. Подготовка Flutter, Docker и локального Supabase описана ниже в разделе «Локальный запуск». Итоги нового этапа — в `ОТЧЁТ-ЭТАП-2.md`, предыдущего — в `ОТЧЁТ-ЭТАП-1.md`.

### Обновление существующего стенда

Новые миграции применяются поверх существующей базы. Существующие записи и серверные результаты команд сохраняются.

```powershell
npx --yes supabase@2.119.0 migration up --local
# Только локальные демонстрационные аккаунты и права для проверок этапа 1.
Get-Content supabase/seed_stage1.sql -Raw | docker exec -i supabase_db_splav-prototype psql -U postgres -d postgres -v ON_ERROR_STOP=1
```

На новом стенде `supabase start` применяет миграции и оба seed-файла. Для рабочего сервера аккаунты создаёт администратор через Supabase Auth, после чего выдаёт членство в `splav.team_members` и назначения в `splav.group_members`. Пользовательская регистрация в приложении отключена. Тестовые аккаунты из seed предназначены для локального стенда.

### Рабочий запуск

Скопируйте `config/workspace.example.json` в `config/workspace-a.local.json`, укажите публичный ключ локального Supabase. Для Android-эмулятора используйте адрес `http://10.0.2.2:54321`, для Windows — `http://127.0.0.1:54321`. Параметр `SPLAV_PROFILE` разделяет локальные экземпляры одного аккаунта.

Для физического телефона укажите доступный ему адрес сервера в отдельном конфигурационном файле. Подготовленный локальный APK использует адрес хоста Android-эмулятора. Для переноса Windows-сборки копируйте весь каталог `build/windows/x64/runner/Debug` с библиотеками и данными приложения.

```powershell
flutter run -d windows --dart-define-from-file=config/workspace-a.local.json
flutter run -d emulator-5554 --dart-define-from-file=config/workspace-b.local.json
```

На экране входа локального стенда доступны `organizer-a@example.com` (администратор), `organizer-b@example.com` (организатор прежних тестовых выездов), `organizer-c@example.com` (только первый тестовый выезд). Пароль всех демонстрационных аккаунтов — `local-splav-demo-2026`. Новый выезд назначается администраторам команды. Дополнительные назначения сотрудников на этом этапе выдаются администратором базы.

После входа обновите каталог и выберите выезды для загрузки. Отметка завершённой загрузки означает, что состав доступен локально. При отключённой сети сохранённый сеанс открывает данные своего аккаунта после перезапуска. Сеанс защищён Windows DPAPI или Android Keystore. Локальные данные и очереди разделяются по окружению, аккаунту и профилю. Выход очищает данные текущего аккаунта после подтверждения при наличии очереди.

На обновлении сохраняется прежний способ вычисления имени локальной базы, включая параметр `SPLAV_GROUP_ID` с прежним значением по умолчанию. Для доступа к прежней очереди используйте те же URL, email, профиль и исходный `SPLAV_GROUP_ID`, что и в прототипе. Выбор другого выезда внутри приложения имя базы не меняет.

База дополнительно привязывается к UUID аккаунта. При изменении UUID для того же email ранее привязанные данные очищаются. В формате v1 UUID владельца отсутствовал, поэтому при первом обновлении он закрепляется за вошедшим аккаунтом.

Прежние группы объединяются в одну команду. Для отсутствовавших в v1 полей сервер задаёт окончание через сутки после начала, сбор за 30 минут до начала, часовой пояс `Europe/Saratov` и базовую стоимость 0. Эти поля можно уточнить в редакторе выезда. Начальная миграция выдаёт права администратора прежнему демонстрационному аккаунту A, а при другом наборе аккаунтов — первому прежнему члену команды по UUID. Назначения доступа к прежним группам сохраняются.

Время выезда вводится и отображается в его часовом поясе. Состояния выезда — черновик, запись открыта, закрыта, в поездке, завершён и отменён. Терминальные состояния блокируют дальнейшее редактирование карточки. Ответственные пока хранятся текстом, управление назначениями доступа выполняется на сервере.

### Люди и совместные заявки

Откройте «Люди» для поиска, создания и изменения карточек. Имя или нормализованный телефон подсказывают возможный дубль. Общий семейный телефон разрешён после проверки совпадения. Администратор видит справочник команды и может явно объединить карточки. Организатор видит созданных им людей и людей доступных выездов, включая контактных лиц. Объединение блокируется, если обе карточки уже имеют участие в одном выезде.

В карточке загруженного выезда откройте «Участники» → «Новая заявка». Добавьте людей из справочника или создайте новых, укажите отдельный контакт. Рост, вес, возраст, одежда и питание задаются для участия в этом выезде. При повторной записи предлагаются параметры последнего загруженного участия; их можно изменить.

Новые участия получают статус «Заявка». Выберите людей и подтвердите их, перенесите в лист ожидания или отмените. Восстановление возвращает ту же запись в заявки. Инструкторы считаются отдельно от лимита клиентов. Если мест не хватает для всего выбора, подтверждение никого не затронет: отмените конфликтующее изменение и выберите меньший состав или лист ожидания. Порядок ожидания задаёт сервер; предложение освободившегося места выполняет организатор. В составе доступна история статусов.

Статус участия отделён от доставки изменения. Очередь, ожидание предыдущей операции, получение принятого сервером результата и конфликты отображаются явно. На экране людей и в составе выезда конфликт можно сравнить с текущими данными, повторить отдельным действием или отменить вместе с зависимыми правками.

SQLite обновляется до v3 без замены старых таблиц и UUID очереди. Старые подтверждённые и ожидающие записи видны без связи. Старые отклонённые записи сохраняются и могут быть явно перенесены в новые заявки. До первого обмена их параметры доступны только для просмотра. При отзыве доступа связанные загруженные данные и черновики удаляются при проверке прав.

Для небольшого объёма этапа 2 справочник передаётся целиком, а состав — согласованным снимком с курсором ревизии команды. Если курсор актуален, сервер возвращает признак отсутствия изменений. Принятая операция остаётся в очереди до атомарного применения соответствующего снимка. Для больших объёмов понадобится постраничный журнал; сейчас снимки не делятся на страницы.

## Локальный запуск

Версии инструментов для проекта — Flutter 3.38.9 с Dart 3.10.8 и Supabase CLI 2.119.0. Для Windows нужны Visual Studio с компонентами разработки классических приложений на C++ и Windows SDK. Для Android нужны Android SDK 36, NDK 27.1.12297006 и эмулятор или подключённое устройство. Локальный Supabase работает через Docker. [Установка Flutter](https://docs.flutter.dev/install) · [Настройка Android](https://docs.flutter.dev/platform-integration/android/setup) · [Локальный Supabase](https://supabase.com/docs/guides/local-development)

Команды ниже выполняются из корня проекта в PowerShell. Если используется SDK из `.tools`, добавьте его в `PATH` для текущего сеанса.

```powershell
# Только если Flutter лежит в .tools
$env:Path = "$(Join-Path $PWD '.tools/flutter/bin');$env:Path"
$env:PUB_CACHE = Join-Path $PWD '.tools/pub-cache'
# Если системный диск заполнен, Gradle может хранить кэш рядом с проектом.
$env:GRADLE_USER_HOME = Join-Path $PWD '.tools/gradle-home'
```

1. Запустите Docker Desktop. Поднимите Supabase с тестовыми аккаунтами и группами из `supabase/seed.sql`.

   ```powershell
   npx --yes supabase@2.119.0 start -x imgproxy,realtime,storage-api,postgres-meta,studio,edge-runtime,logflare,vector,supavisor,mailpit
   npx --yes supabase@2.119.0 status
   flutter pub get
   ```

2. Скопируйте `config/client.example.json` в `config/client-a.local.json` и `config/client-b.local.json`. В `SUPABASE_ANON_KEY` укажите публичный ключ локального API (`Publishable` или `anon`). В конфигурации B задайте `SPLAV_EMAIL` равным `organizer-b@example.com` и `SPLAV_PROFILE` равным `client-b`. Оба аккаунта используют демонстрационный пароль из примера. В конфигурации Android-эмулятора задайте `SUPABASE_URL` равным `http://10.0.2.2:54321`. В Windows используйте `http://127.0.0.1:54321`.

3. Запустите клиенты в отдельных терминалах. Идентификатор эмулятора возьмите из `flutter devices`.

   ```powershell
   flutter run -d windows --dart-define-from-file=config/client-a.local.json --dart-define=SPLAV_DEMO=true
   flutter run -d emulator-5554 --dart-define-from-file=config/client-b.local.json --dart-define=SPLAV_DEMO=true
   ```

   Оба клиента можно запустить на Windows. Оставьте адрес `127.0.0.1` в обоих файлах и выполните вторую команду с `-d windows`. Профиль определяет отдельный файл SQLite. HTTP на Android разрешён в debug-сборке для локального теста. Параметры тестового входа компилируются в приложение и предназначены для стенда с вымышленными данными.

## Проверка

1. Загрузите группу на обоих клиентах. Должно отображаться одно свободное место.
2. Включите «Без сети» на каждом клиенте и добавьте разных участников. Обе записи должны ожидать подтверждения.
3. Закройте один клиент и запустите его с тем же файлом конфигурации при отключённой связи. Проверьте сохранённую запись и очередь. Для управляемого сценария без отключения ОС заблокируйте локальный API на время перезапуска либо выполните автоматический тест ниже.
4. Восстановите связь на обоих клиентах. После обмена в обоих списках должен быть один и тот же подтверждённый участник. На устройстве с проигравшей заявкой отображается причина «Свободных мест нет». Если один клиент закончил обмен раньше другого, нажмите «Синхронизировать» на обоих.

```powershell
flutter analyze
flutter test test/prototype_sync_test.dart

# Используйте публичный ключ локального API из вывода status.
$env:SPLAV_SUPABASE_KEY = '<local publishable or anon key>'
python scripts/server_acceptance.py

```

Обычные тесты Flutter проверяют SQLite и сбои через тестовый транспорт. Интеграционный тест использует две независимые SQLite-базы, два сеанса Supabase Auth и настоящий PostgreSQL. Он закрывает и вновь открывает SQLite и моделирует потерю ответа после того, как сервер его сформировал. Запись повторно отправляется с тем же UUID. Серверная проверка и интеграционный тест используют отдельные тестовые группы. Для повторного прогона нужен свежий локальный seed. Команда `npx --yes supabase@2.119.0 db reset --local` пересоздаёт данные локального стенда. После сброса для ручной проверки задайте новые значения `SPLAV_PROFILE`, чтобы начать с чистых локальных баз.

## Как устроен прототип

- `lib/features` — адаптивная карточка тестового выезда и список участников. Подтверждённые, ожидающие и отклонённые записи различаются визуально.
- `lib/core` — Drift, локальные данные группы и очередь отправки. Изменение становится подтверждённым в интерфейсе при применении серверного журнала. Применение страницы, обновление курсора и удаление подтверждённых команд выполняются вместе.
- `supabase/migrations` — модель группы, человека и записи, серверный журнал и RPC. PostgreSQL проверяет доступ, сериализует конкурирующие записи одной группы и сохраняет результат по UUID операции для безопасного повтора.

Этот демонстрационный режим проверяет добавление участника в одну группу. При конфликте последнего места запись сохраняется локально как отклонённая. Для справочника людей, совместных заявок и листа ожидания используйте рабочий режим, описанный в начале README.
